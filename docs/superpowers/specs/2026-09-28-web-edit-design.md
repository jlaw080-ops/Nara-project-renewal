# 웹 입력 기능 설계 (웹 UI 2단계)

- 상태: 설계 확정, 구현 계획 작성 전
- 작성: 2026-09-28
- 앞 문서: `2026-09-27-web-query-ui-design.md`(1단계, 읽기 전용 조회)

## 요약

- **주제**: 1단계 조회 화면의 상세 화면에서 사업 정보·진행현황·실행부서·신재생 계획을 입력하고 고친다
- **배경**: 웹이 구글 시트를 대신하려면 조사 결과를 웹에 넣을 수 있어야 한다. 3단계(클라우드) 전까지는 팀원이 시트를 계속 고치고 다시 이관한다
- **결론**: 서버가 그리는 묶음별 폼으로 입력한다. 웹 수정은 `edit_log`에 남긴다. 사람이 정한 진행현황은 자동 판정이 덮지 못하게 잠근다. 시트 재이관은 지난 이관 뒤 시트에서 실제로 바뀐 칸만 반영하고, 그 칸이 웹 입력을 덮으면 목록으로 알린다

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 입력 범위 | 사업 정보 9칸, 진행현황 사람 판정, 실행부서 확정, 신재생 설비 계획 | 2026-09-28 사용자 선택(네 가지 전부) |
| 입력 방식 | 상세 화면의 묶음별 폼. 서버가 그린다. JS 없음 | 사용자가 접근안 A 선택. 1단계와 같은 방식이고 조사는 사업 하나씩 한다 |
| 사람 판정 | 잠근다. 자동 판정이 그 사업을 건너뛴다. "자동 판정에 다시 맡기기"로 푼다 | 사용자 선택. 지금 규칙은 앞으로 가는 판정이면 사람 판정도 덮는다 |
| 시트 재이관 | 계속한다. 팀원이 시트를 고친다 | 사용자 답 |
| 충돌 규칙 | 지난 이관 뒤 시트에서 **실제로 바뀐 칸만** 시트가 이기고, 웹 입력을 덮으면 알린다 | 사용자 선택. TSV에는 칸별 수정 시각이 없어 글자 그대로 "시트가 이긴다"면 옛 값이 웹 입력을 매번 되돌린다 |
| 사용자 | 2단계는 혼자, 로컬 | 여러 사람 동시 수정은 3단계 |

## 저장 구조

### 새 표

| 표 | 칸 | 쓰임 |
|---|---|---|
| `edit_log` | `id`, `project_id`, `field`, `old_value`, `new_value`, `edited_at` | 웹 수정 기록. 상세 화면의 수정 이력과 이관 알림의 근거 |
| `sheet_memory` | `project_id`, `field`, `value`, `imported_at` (기본키 `project_id, field`) | 칸마다 지난 이관 때의 시트 값 |

`field` 값은 사업 정보 9칸 이름(`address`, `start_date`, `end_date`, `floor_area`, `zeb_grade`, `re_ratio`, `etc_cert`, `guide_equip`, `note`)과 `verdict`, `exec_dept`, `energy`다. 신재생은 줄 목록을 정렬한 한 문자열(예: "PV 20, 지열 10")로 비교한다.

`sheet_memory`는 스키마를 도입할 때 지금 DB 값으로 채운다. 도입 시점까지 웹 수정이 없으므로 지금 값이 곧 지난 이관 값이다.

### 묶음별 저장

| 묶음 | 저장 |
|---|---|
| 사업 정보 | `project` 칸을 UPDATE, `updated_at` 갱신 |
| 진행현황 | `status_check`에 `decided_by='human'` 한 줄 추가. 사유 필수 |
| 실행부서 | `dept_check`에 `decided_by='human'` 한 줄 추가 |
| 신재생 | 그 사업의 `energy_plan` 줄을 새 목록으로 바꾼다. `entered_by='human'` |

한 번의 저장은 값 변경과 `edit_log` 기록을 한 트랜잭션으로 묶는다. 값이 그대로인 칸은 기록하지 않는다.

### 쓰기 연결

- 조회(GET)는 1단계 그대로 `mode=ro` 연결을 쓴다
- 저장(POST)만 `mode=rw` URI로 연다. `nara.db.connect`는 없는 파일을 만들기 때문에 쓰지 않는다
- `busy_timeout` 5초. 수집이 쓰는 중이면 기다렸다 쓴다. 넘으면 "수집이 DB를 쓰고 있다, 잠시 뒤 다시 저장하라"를 보이고 입력값은 폼에 남긴다

## 사람 판정 잠금

- 최신 `status_check`의 `decided_by`가 `human`이면 `nara enrich status`의 대상 조회(`pending_status_projects`)에서 뺀다
- "자동 판정에 다시 맡기기"는 현재 판정을 그대로 복사한 줄을 `decided_by='release'`로 쌓는다. `verdict`가 NOT NULL이라 판정을 비울 수 없다. 이력에는 "잠금 해제"로 보인다
- 잠금 해제 뒤에는 `should_record`의 기존 규칙이 적용된다. `release`는 규칙 판정이 아니므로 규칙 판정이 밀어내지 못하고, 뉴스·LLM 판정은 앞으로 갈 때 쌓인다
- 시트 이관이 진행현황을 바꾸면(아래) 잠금도 풀린다. `imported` 줄이 최신이 되기 때문이다

## 화면

### 상세 화면

- 1단계 표시 묶음마다 "고치기" 링크를 둔다. 누르면 그 묶음만 폼으로 바뀐다(`/project/<id>?edit=info|verdict|dept|energy`)
- 저장하면 상세 화면으로 돌아간다(POST 뒤 redirect). 맨 위에 바꾼 칸을 한 줄로 알린다. 예: "착공일·연면적을 고쳤습니다"
- 검증에 실패하면 입력값을 그대로 담은 폼을 다시 보이고, 칸 옆에 이유를 적는다
- 맨 아래에 수정 이력(`edit_log`, 최신순): 시각·칸·이전 값 → 새 값
- 판정 주체 표시에 `release` → "잠금 해제"를 더한다

### 검증

| 칸 | 받는 값 | 거부 |
|---|---|---|
| 착공일·준공일 | `YYYY-MM-DD` 또는 빈칸 | 형식 오류, 준공일이 착공일보다 빠름 |
| 착공일, 최신 판정이 "착공 전" | 확정 착공일을 받지 않는다 | "착공 전이면 예정은 비고에 적으세요". 원 명세 규칙: 착공 전이면 확정 착공일을 기록하지 않는다 |
| 연면적 | 0보다 큰 숫자, 쉼표 허용, 또는 빈칸 | 숫자가 아님 |
| 주소·ZEB·신재생 비율·기타 인증·관급 장비 | 글자, 앞뒤 공백 제거, 200자까지 | 상한 초과 |
| 비고 | 글자, 2,000자까지 | 상한 초과 |
| 진행현황 | 착공 전·시공 중·준공 완료·미확인 중 하나, 사유 필수 | 목록 밖 값, 사유 없음 |
| 실행부서 | 글자(필수), 근거 문장(선택). 기존 후보의 근거 문장을 눌러 채울 수 있다 | 빈 값 |
| 신재생 | 줄마다 에너지원과 용량(kW, 0보다 큼). 줄 추가·삭제 | 같은 에너지원 두 줄, 용량 오류. 단가표에 없는 에너지원은 받되 예상가 "없음"으로 보인다 |

진행현황을 뒤로 돌리는 것(예: 준공 완료 → 시공 중)은 막지 않는다. 사람이 기계의 잘못을 고치는 경로가 이것이다.

### 목록 화면

편집하지 않는다. 최신 판정이 사람 판정이면 진행현황 옆에 "(사람)"을 붙여 잠긴 사업을 보인다.

## 시트 재이관

`nara migrate tsv`가 칸마다 `sheet_memory`와 비교한다.

| 시트 값 | 처리 |
|---|---|
| 지난 이관 값과 같다(팀원이 안 고침) | 건드리지 않는다. 웹 입력이 남는다 |
| 지난 이관 값과 다르다(팀원이 고침) | 시트 값으로 덮고 `sheet_memory`를 갱신 |
| 위와 같고 그 칸이 `edit_log`에 있다 | 덮은 뒤 이관 결과에 "사업 · 칸 · 웹 값 → 시트 값" 목록으로 알린다 |
| 시트 칸이 비었다 | 건드리지 않는다(현행 유지) |

진행현황·실행부서·신재생도 같은 규칙이다. 지금은 셋 다 처음 한 번만 넣고 이후 이관은 무시한다. 바뀌면 진행현황·실행부서는 `imported` 줄을 새로 쌓고, 신재생은 목록을 시트 값으로 바꾼다. 그래서 웹에서 지운 신재생 줄은 시트가 바뀌지 않는 한 되살아나지 않는다. 지금 구현은 사업에 없는 에너지원이면 다시 넣는다.

`sheet_memory`에 없는 칸(새 사업, 새로 채운 칸)은 "바뀌었다"로 본다.

## 보안

| 위험 | 막는 방법 |
|---|---|
| 다른 웹사이트가 내 브라우저로 127.0.0.1에 저장 요청을 보낸다(CSRF) | POST는 `Origin`이 이 서버와 같을 때만 받는다. `Origin`이 없으면 `Sec-Fetch-Site: same-origin`일 때만 받는다. 둘 다 없으면 거부 |
| DNS 리바인딩으로 외부 페이지가 화면을 읽는다 | `TRUSTED_HOSTS = ["127.0.0.1", "localhost"]`. 1단계 리뷰에서 보류한 minor를 여기서 닫는다 |
| 조회 중에 자료가 바뀐다 | GET은 계속 읽기 전용 연결을 쓴다. 쓰기는 POST만 |
| 폼 값이 SQL에 들어간다 | 칸 이름은 허용 목록으로만 받고 값은 자리표시자로 넘긴다 |

## 테스트

- 검증 표의 거부 사례마다 하나. 거부 뒤 입력값이 폼에 남는다
- 값이 같은 칸은 `edit_log`에 쌓이지 않는다. 저장과 기록은 함께 되거나 함께 안 된다
- 잠금: 사람 판정인 사업을 `pending_status_projects`가 돌려주지 않는다. 잠금 해제 뒤에는 돌려준다
- 이관: 표의 네 경우, 알림 목록, 웹에서 지운 신재생 줄이 되살아나지 않음, 시트가 사람 판정을 바꾸면 잠금이 풀림
- 보안: 다른 출처의 POST, 출처 헤더 없는 POST, 낯선 Host는 거부
- 동시 쓰기: 다른 연결이 쓰기 잠금을 쥔 동안 저장하면 기다렸다 성공한다. 시간을 넘기면 이유를 보이고 입력값을 남긴다
- 1단계 테스트는 전부 그대로 통과한다. GET이 읽기 전용이라는 테스트도 유지한다

## 3단계로 넘기는 판단

- **여러 사람 동시 수정.** 같은 사업을 두 사람이 연 채 저장하면 나중 저장이 이긴다. 2단계는 혼자 쓰므로 막지 않는다. 3단계에서 저장 시 "그새 바뀜" 검사를 넣는다
- **누가 고쳤나.** `edit_log`에 사용자 칸이 없다. 로그인이 생기는 3단계에서 더한다
- **시트 재이관 종료.** 팀원이 웹을 쓰기 시작하면 이관과 `sheet_memory`는 필요 없어진다
- **1단계 보류 minor 7건**은 그대로 보류한다(`TRUSTED_HOSTS`만 이번에 닫는다)
