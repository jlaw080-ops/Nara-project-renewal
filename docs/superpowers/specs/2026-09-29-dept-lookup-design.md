# 공고 첨부에서 실행부서 찾기 설계 (4단계)

- 상태: 설계 확정, 구현 계획 작성 전
- 작성: 2026-09-29
- 앞 문서: `2026-09-17-nara-collector-design.md`(원 명세 「4단계 · 부서 조회」), `2026-09-28-cloud-team-design.md`(3단계에서 이 작업을 4단계로 미룸)
- 근거 스킬: `notice-dept-contact-lookup` 1부(공고문에서 실행부서 찾기)

## 요약

- **주제**: 나라장터 공고에 붙은 공고문을 내려받아 읽고 사업을 실제로 맡은 실행부서를 찾아 기록하는 단계를 앱에 넣는다
- **배경**: 나라장터의 "수요기관 부서명"은 대부분 계약부서(재무과·회계과)다. 실행부서는 첨부 공고문 안에만 적혀 있다. 지금은 시트에서 옮긴 192건만 실행부서가 있고 앱이 새로 모은 사업 76건은 빈칸이다
- **결론**: 공고 API가 주는 다운로드 주소로 첨부를 바로 받는다. 브라우저 자동화는 쓰지 않는다. 규칙으로 후보를 찾아 하나로 좁혀지면 확정하고, 애매하면 Claude가 고른 근거 문장을 원문과 글자 단위로 대조해 맞을 때만 확정한다. 확정하지 못한 건은 "검토 필요"로 두고 사람이 웹 화면에서 고른다

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 범위 | 실행부서만 찾는다. 과장 직통번호는 사람이 입력한다 | 사용자 선택. 직통번호는 지자체마다 직원안내 페이지 구조가 달라 따로 다룬다 |
| 첨부 받는 길 | 다운로드 주소로 직접 받는다(접근안 A) | 사용자 선택. 2026-09-29 실측에서 API가 준 주소와 공고번호로 만든 주소 모두 파일이 그대로 받아졌다 |
| 애매한 건 | Claude가 고르고, 근거 문장을 원문과 대조해 맞을 때만 확정한다 | 사용자 선택 |
| 대상과 주기 | 관심기관은 09·15시, 비관심기관은 평일 12시에 요일 그룹별로 본다 | 사용자 선택. 낙찰 조회와 같은 주기다 |
| 확정 원칙 | 문서에서 읽은 것만 확정한다. 조직도나 사업 성격으로 짐작하지 않는다. 근거가 없으면 빈칸이다 | 스킬의 핵심 원칙 |

## 첨부 받기

### 실측 결과 (2026-09-29)

| 경우 | 결과 |
|---|---|
| 앱이 수집한 공고 | 공고 API 원본(`notice.raw_json`)에 `ntceSpecFileNm1~10`(파일 이름)과 `ntceSpecDocUrl1~10`(다운로드 주소)이 있다. 주소로 GET하면 파일이 온다 |
| 시트에서 옮긴 옛 공고 | 원본이 없다. 주소 형식이 `…/UntyAtchFile/downloadFile.do?bidPbancNo=<공고번호>&bidPbancOrd=<차수>&fileType=&fileSeq=<순번>&prcmBsneSeCd=05`로 일정하다. 순번 1·2는 파일이 왔고, 없는 순번 9는 422와 JSON 오류를 돌려줬다. 파일 이름은 `Content-Disposition` 머리에 있다 |

스킬 문서의 "체크박스 클릭 → 다운로드 버튼만 된다"는 새 나라장터 공고 화면을 조작하던 경로다. API가 주는 주소는 그와 다른 경로이고 암호화되어 있지 않다.

### 파일 목록과 고르기

- 파일 목록은 API 원본이 있으면 거기서 읽는다. 없으면 순번 1부터 10까지 차례로 요청하고 파일이 아닌 응답이 오면 멈춘다
- 고르는 순서는 스킬을 따른다. 이름에 `공고`가 든 파일이 먼저이고 없으면 `과업|지침|제안`이 든 파일이다
- 같은 문서가 여러 형식으로 올라와 있으면(예: `공고문.hwpx`와 `공고문.pdf`) HWPX → PDF → HWP 순으로 하나만 받는다. HWPX는 XML이라 글자가 정확하고 HWP 바이너리 해석은 가장 불안정하다
- 한 공고에서 최대 두 문서까지 받는다. 공고문에서 부서를 못 찾으면 과업지시서·지침서를 본다

### 받아 두기

- 파일은 `data/attachments/<공고번호>/<순번>_<파일 이름>`에 둔다. 추출한 텍스트는 같은 폴더에 `.txt`로 둔다
- 첨부 폴더 위치는 DB 파일이 있는 폴더의 `attachments`로 정한다. 웹과 명령이 같은 규칙으로 찾는다
- 이미 받은 파일은 다시 받지 않는다. 받은 기록은 `attachment` 표에 남긴다(표는 원 명세 때 이미 만들어 두었다)
- 첨부는 백업하지 않는다. 언제든 다시 받을 수 있다

## 텍스트 추출

| 형식 | 판별 | 방법 |
|---|---|---|
| HWPX | 파일 앞 4바이트 `PK\x03\x04` | zip 안 `Contents/section*.xml`에서 태그를 걷어 낸다 |
| PDF | `%PDF` | `pypdf`로 쪽마다 글자를 뽑는다 |
| HWP | OLE 서명 `D0 CF 11 E0 A1 B1 1A E1` | `olefile`로 `BodyText` 흐름을 열고, 압축을 풀어 문단 글자 레코드(태그 67)를 읽는다 |

- 형식은 확장자가 아니라 파일 앞부분으로 판별한다. 서버가 보낸 이름이 깨져 있을 수 있다
- 스킬은 PDF에 PyMuPDF를 쓴다. PyMuPDF는 AGPL 라이선스라 회사 서버에 올릴 코드에는 BSD 라이선스인 `pypdf`를 쓴다
- HWP 본문에 섞인 서로게이트 문자는 UTF-8로 저장할 때 대체 문자로 바꾼다

## 부서 판정

### 1. 규칙

스킬의 `find_dept.py`를 옮긴다.

- 신호어("사업 담당", "사업 관련", "담당 부서", "주관 부서", "설계서 열람", "과업 관련", "용역에 관한", "문의처", "접수처" 등) 뒤 200자 안에서 부서명(`…과|국|실|단|소|센터|본부|사업소|담당관`)을 찾는다
- 신호어 바로 뒤 90자 안에서 찾은 부서는 무게 3, 그 밖은 1을 준다
- 뺄 것: 재무·회계·경리·세정·예산·계약·감사 계열 부서, 시설명·기관명(조달청, 전시실 등), 조사 '과'가 붙은 가짜 부서("이 사업과", "다음과")
- 칸을 맞추려고 글자 사이를 띄운 부서명(`행 정 과`)은 붙여서 읽는다. 한 글자씩 띄운 한글 세 글자 이상이 부서 끝말(과·국·실·소·단)로 끝날 때만 붙인다
- 실행부서는 과 단위로 적는다. `문화관광과 관광팀`이면 `문화관광과`로 적고 팀 이름은 근거 문장에만 남긴다. 팀·계·담당만 있고 과가 없으면 확정하지 않고 후보로 둔다
- 뺀 계약 계열 부서 중 첫 번째는 계약부서로 적는다

**규칙 확정 조건**: 후보가 정확히 하나이고, 그 후보가 무게 3(신호어 바로 뒤)을 받았고, 과 단위 이름일 때. 판정 주체는 `rule`이다.

### 2. Claude

규칙 후보가 없거나 둘 이상이면 Claude에 묻는다.

- 보여 줄 글: 신호어 앞뒤 300자 구간을 모은 것과 문서 끝 1,500자(문의처는 대개 끝에 있다). 합쳐 6,000자를 넘지 않는다
- 받을 답: 세 줄. `실행부서: <과 이름 또는 없음>`, `계약부서: <이름 또는 없음>`, `근거: <원문에서 그대로 옮긴 문장>`
- 지시: 문서에 적힌 것만 답한다. 계약·입찰·개찰 문의 부서는 실행부서가 아니다. 확신이 없으면 `없음`이라고 답한다

### 3. 원문 대조

Claude 답은 아래 셋을 모두 통과할 때만 확정한다. 판정 주체는 `llm`이다.

1. 근거 문장이 추출한 원문에 글자 그대로 있다. 공백과 줄바꿈은 무시하고 비교한다
2. 실행부서 이름이 근거 문장 안에 있다. 공백은 무시한다
3. 실행부서가 계약 계열 부서(규칙의 뺄 목록)가 아니다

하나라도 어긋나면 Claude 답을 후보로만 남긴다. 키가 없거나 호출이 실패하면 규칙 후보만 남긴다.

### 모델

진행현황 판정과 실행부서 판정은 `nara/llm.py`의 모델 이름 하나(`claude-opus-5`)를 함께 쓴다. 이 이름은 지금도 쓸 수 있는 모델이라 바꾸지 않는다(2026-09-30 claude-api 참고 자료로 확인. 설계 때 "목록에 없는 이름"이라고 적은 것은 잘못이었다).

## 기록

### 표 변경

| 표 | 변경 |
|---|---|
| `dept_check` | `confirmed INTEGER NOT NULL DEFAULT 1`(확정 여부), `note TEXT`(못 찾은 사유) 칸을 더한다. 이미 있는 DB는 `ALTER`로 더한다. 기존 줄(시트·사람)은 기본값 1로 확정이 된다 |
| `attachment` | `seq INTEGER`(파일 순번) 칸을 더한다 |

### 결과별 기록

| 결과 | `dept_check` 기록 | 목록 표시 |
|---|---|---|
| 규칙·Claude 확정 | 실행부서·계약부서·근거 문장·원본 파일명, `confirmed=1`, 주체 `rule`·`llm` | 실행부서 |
| 후보만 있음 | 후보마다 한 줄, `confirmed=0`, 주체 `rule`·`llm` | 검토 필요 |
| 못 찾음 | 실행부서 빈칸, `confirmed=0`, `note`에 사유("첨부 없음", "공고문에 계약부서만 있음" 등) | 빈칸 |
| 다운로드 실패 3회 | 실행부서 빈칸, `note`="수동 확인" | 빈칸 |

- 목록·상세의 "지금 실행부서"와 동시 수정 확인의 버전 표시는 `confirmed=1`인 줄만 본다
- 사람이 웹에서 후보를 고르거나 직접 적으면 `confirmed=1`, 주체 `human`인 줄이 생긴다. 확정된 사업은 자동 조회가 다시 보지 않는다

### 조회 대상

- 확정된 실행부서가 없는 사업만 본다. 시트에서 옮긴 값과 사람이 정한 값은 건드리지 않는다
- 한 번 자동 조회한 사업은 아래 둘 중 하나일 때만 다시 본다
  - 가장 최근 공고의 번호가 마지막 자동 조회 때 기록한 공고번호와 다르다(재공고 등). 수집은 최근 3일 공고를 날마다 다시 받아 수집 시각이 바뀌므로 시각이 아니라 공고번호로 비교한다
  - 마지막 자동 조회가 "다운로드 실패"로 끝났다
- 공고가 여럿이면 최근 공고부터 본다

## 명령과 예약

- 새 명령: `nara enrich dept [--tier focus|rest|all] [--group 1-5] [--limit 300] [--budget 1200] [--db]`
- 실행 기록은 `run_log`의 `enrich dept`로 남는다. 실행 뒤 한 줄로 보인다: `실행부서 — 조회 N건 / 확정 규칙 a·Claude b / 검토 필요 c / 못 찾음 d / 실패 e`
- 슬롯 순서

| 슬롯 | 단계 |
|---|---|
| `09`·`15` | 수집 → 낙찰 조회(관심) → 진행현황(관심) → 실행부서(관심) |
| `12` 평일 | 수집 → 낙찰 조회(비관심, 요일 그룹) → 실행부서(비관심, 같은 그룹) |
| `12` 주말 | 수집 |

- 목록 머리 "단계별 마지막 실행"에 `실행부서`를 더한다

## 화면

| 위치 | 변경 |
|---|---|
| 목록 실행부서 칸 | 확정값만 보인다. 후보만 있으면 "검토 필요"로 보인다 |
| 목록 필터 | "실행부서 검토 필요"를 더한다 |
| 상세 실행부서 | 확정값과 판정 주체(규칙·Claude·사람·시트)를 보인다. 후보마다 근거 문장과 원본 파일명을 보인다. 못 찾았으면 사유를 보인다. "고치기"로 후보를 고르는 기존 폼은 그대로 쓴다 |
| 상세 공고 | 받아 둔 첨부 목록과 내려받기 링크를 보인다 |

첨부 내려받기는 `GET /attachment/<id>`다. 로그인한 사람만 받는다. `attachment` 표의 번호로만 파일을 찾고, 찾은 경로가 첨부 폴더 안에 있는지 확인한 뒤 내준다. 폴더 밖이면 404다.

## 오류 처리

- 다운로드는 파일당 30초 제한, 30MB 상한이다. 받은 내용의 앞부분이 PDF·HWPX·HWP 서명이 아니면 파일로 치지 않는다(오류 안내 JSON·HTML 거르기)
- 나라장터에 부담을 주지 않도록 한 번에 한 건씩 받고 요청 사이에 0.5초 쉰다
- 서버가 보낸 파일 이름에서 경로 문자(`/`, `\`, `..`)와 제어 문자를 걷어 내고 100자로 자른다
- 다운로드 실패는 `dept_check`에 사유 "다운로드 실패" 줄로 남고 다음 회차에 다시 본다. 같은 공고에서 연달아 3회 실패하면 "수동 확인"으로 남기고 새 공고가 오기 전에는 다시 시도하지 않는다
- 텍스트 추출에 실패하면 다음 파일로 넘어간다. 모두 실패하면 사유를 남긴다
- Claude 실패는 실행 전체의 실패로 치지 않는다. 요약에 따로 센다
- 시간 예산(기본 20분)을 넘기면 처리한 데까지 저장하고 멈춘다. 다음 회차가 이어서 본다

- 파일 받기: API 원본에서 목록 읽기, 순번 요청이 파일 아닌 응답에서 멈춤, 고르는 순서와 형식 순서, 위험한 파일 이름 다듬기, 30MB 상한, 서명 확인. 네트워크는 가짜로 바꾼다
- 텍스트 추출: 테스트 안에서 만든 작은 HWPX·PDF와 HWP 레코드 바이트로 확인한다
- 규칙: 스킬에 적힌 실제 실패 사례를 옮긴다. 계약·실행 짝에서 실행부서 고르기, 재무과 빼기, "이 사업과" 오인 막기, `행 정 과` 붙여 읽기, 팀을 과 단위로 줄이기, 팀만 있으면 확정하지 않기
- 원문 대조: 원문에 없는 근거 문장, 근거에 없는 부서명, 계약부서 답은 후보로만 남고 정상 답은 확정된다. Claude는 가짜로 바꾼다
- 흐름: 시트·사람 부서는 건너뛴다, 새 공고가 오면 다시 본다, 3회 실패하면 "수동 확인", 시간 예산을 넘기면 멈춘다
- 화면: 목록에 확정값만 보인다, 검토 필요 필터, 첨부 내려받기는 로그인이 필요하다, 폴더 밖 경로는 404
- 1~3단계 테스트는 전부 그대로 통과한다

### 실데이터 검증

시트에서 옮긴 192건의 실행부서는 사람이 공고문을 읽고 찾은 값이다. 이 값을 정답지로 쓴다.

- DB 사본에서 이 사업들의 확정값을 지우고 자동 조회를 돌린 뒤, 시트 값과 비교한다(공백을 빼고 과 단위로 비교)
- 목표는 **자동 확정한 값 중 시트와 다른 것 0건**이다
- 어긋나면 규칙을 고치거나, 그 유형은 확정하지 않고 후보로 돌린다
- 일치 건수, 검토 필요 건수, 어긋난 사례를 보고한다
- 원본 `data/nara.db`에는 쓰지 않는다
