# 클라우드 배포·로그인·팀 공유 설계 (웹 UI 3단계)

- 상태: 설계 확정, 구현 계획 작성 전
- 작성: 2026-09-28
- 앞 문서: `2026-09-27-web-query-ui-design.md`(1단계), `2026-09-28-web-edit-design.md`(2단계)

## 요약

- **주제**: 로컬에서만 돌던 조회·입력 화면과 수집을 무료 클라우드 서버 한 대로 옮기고, 팀원이 각자 계정으로 로그인해 쓰게 한다
- **배경**: 웹이 구글 시트를 대신하려면 팀원이 사용자 PC 밖에서 접속해야 한다. 수집도 사용자 PC가 꺼지면 멈춘다
- **결론**: Oracle Cloud 서울 리전 무료 가상서버에 앱·수집·백업을 함께 둔다. 앞단의 Caddy가 무료 서브도메인에 HTTPS를 붙인다. 로그인은 사람별 이메일·비밀번호다. 두 사람이 같은 묶음을 고치면 나중 저장을 막고 알린다. DB는 매일 구글 드라이브로 백업한다

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 개인정보 | 공무원 담당자 이름·연락처를 서버에 그대로 저장 | 2026-09-28 사용자 답: "저장해도 된다". 나라장터 공개 정보 |
| 수집 위치 | 서버에서 돌린다 | 사용자 선택. 사용자 PC를 꺼도 수집이 멈추지 않는다 |
| 로그인 | 사람별 이메일 + 비밀번호 | 사용자 선택 |
| 서버 | Oracle Cloud 상시 무료 ARM 가상서버, 서울 리전 | 사용자가 무료를 원함. 2026년 6월 기준 2코어·12GB로 이 앱에 충분하다. 춘천 리전은 ARM 무료 대상이 아니다 |
| 주소 | 무료 서브도메인(DuckDNS), Let's Encrypt 인증서 자동 | 사용자 선택. 비밀번호 로그인에는 HTTPS가 필수다 |
| 배포 방식 | 가상서버에 직접 설치(접근안 A). SQLite 유지 | 사용자 선택. 지금 코드를 거의 그대로 옮긴다 |
| 백업 | 매일 구글 드라이브로 | 사용자 확인. 무료 조건이 예고 없이 바뀐 적이 있어 서버 밖에 둔다 |

## 서버 구성

| 부분 | 하는 일 |
|---|---|
| Caddy | `https://<이름>.duckdns.org`로 받아 앱에 넘긴다. 인증서를 자동으로 받고 갱신한다 |
| 앱 | 지금의 Flask 앱을 waitress로 띄운다. `127.0.0.1:8000`에만 열려 밖에서 직접 들어올 수 없다 |
| 수집 예약 | systemd timer가 매일 09·12·15시에 `nara run slot`을 부른다 |
| 백업 예약 | systemd timer가 매일 03시에 `nara backup`을 부른다 |
| DB | `/srv/nara/data/nara.db` 한 파일 |

### 비밀값

- 조달청 인증키(`G2B_API_KEY`), LLM 키(`ANTHROPIC_API_KEY`), 세션 서명 키(`NARA_SECRET_KEY`), 서버 주소(`NARA_HOST`)는 서버의 `/srv/nara/.env`에만 둔다. 파일 권한은 소유자만 읽기(600)
- 저장소는 공개(public)다. 배포 파일(`deploy/`)에는 값을 적지 않고 이름만 적는다
- 세션 서명 키가 없으면 앱이 뜨지 않는다. 기본값으로 대신하지 않는다

### 배포

- 처음 설치 순서는 `deploy/setup.md`에 적는다: Oracle 계정·가상서버 만들기, 방화벽 80·443 열기, DuckDNS 주소 등록, Caddy·uv 설치, 저장소 받기, `.env` 만들기, systemd 서비스·타이머 등록, rclone 구글 드라이브 연결
- 이후 갱신은 `deploy/update.sh` 하나로 한다: `git pull` → `uv sync` → 서비스 재시작
- 설정 파일 원본(`deploy/nara-web.service`, `deploy/nara-slot@.service`, `deploy/nara-slot@.timer`, `deploy/nara-backup.*`, `deploy/Caddyfile`)은 저장소에 둔다
- 계정 만들기와 카드 인증은 사용자가 한다. 계정 생성과 결제 수단 입력은 도구가 대신할 수 없다

### 처음 옮기기

- 사용자 PC의 `data/nara.db`를 SQLite 백업 기능으로 복사해 서버로 한 번 올린다
- 옮긴 뒤 사용자 PC의 작업 스케줄러 수집을 끈다. 두 곳에서 수집하면 결과가 엇갈린다

## 로그인과 계정

### 표

| 표 | 칸 |
|---|---|
| `app_user` | `id`, `email`(소문자, UNIQUE), `name`, `password_hash`, `must_change`(임시 비밀번호 여부), `active`, `created_at`, `last_login_at` |
| `login_attempt` | `id`, `email`, `ok`, `at` |
| `edit_log` | `user_id` 칸을 더한다(NULL 허용) |

### 계정 관리 명령

| 명령 | 하는 일 |
|---|---|
| `nara user add <이메일> --name <이름>` | 계정을 만들고 임시 비밀번호를 한 번만 보인다 |
| `nara user reset <이메일>` | 임시 비밀번호를 다시 만든다 |
| `nara user disable <이메일>` | 로그인을 막는다. 수정 기록은 남긴다 |
| `nara user list` | 이메일·이름·사용 여부·마지막 로그인 |

- 웹 관리 화면은 두지 않는다. 계정 관리는 서버에 접속할 수 있는 사람이 한다
- 임시 비밀번호는 16자 무작위(`secrets`). 첫 로그인에서 비밀번호 바꾸기 화면으로 먼저 보낸다
- 새 비밀번호는 10자 이상, 임시 비밀번호와 달라야 한다

### 로그인 규칙

- 로그인하지 않으면 모든 화면이 로그인 화면으로 넘어간다. 로그인 화면·정적 파일만 예외
- 비밀번호는 Werkzeug `generate_password_hash`(scrypt)로만 저장한다. Flask에 들어 있어 새 의존성이 없다
- 세션은 Flask 서명 쿠키. `Secure`(HTTPS일 때), `HttpOnly`, `SameSite=Lax`, 14일 유지. 로그아웃하면 지운다
- 같은 이메일로 15분 안에 실패 5번이면 15분 동안 그 이메일의 로그인을 막는다. 막힌 동안에는 비밀번호가 맞아도 막는다
- 없는 이메일·틀린 비밀번호·사용 중지 계정은 모두 "이메일 또는 비밀번호가 맞지 않습니다"로 답한다. 잠금만 "잠시 뒤 다시 시도하세요"로 따로 알린다
- 로컬 `nara serve`도 로그인이 켜져 있다. 혼자 쓸 때는 자기 계정 하나를 만든다

### 권한과 기록

- 로그인한 사람은 모두 조회·입력한다. 역할 구분은 두지 않는다
- 웹 저장·사람 판정·부서 확정·잠금 해제는 `edit_log.user_id`에 누가 했는지 남긴다. 잠금 해제도 이제 `edit_log`에 남긴다(칸 `verdict`, 이전·새 값은 판정 그대로)
- 상세 화면의 수정 이력에 이름을 보인다. 2단계 때 쌓인 기록은 "(2단계 기록)"으로 보인다
- 2단계의 같은 출처 확인(CSRF)은 그대로 둔다. `TRUSTED_HOSTS`에 `.env`의 `NARA_HOST`를 더한다

## 동시 수정

- 묶음 폼을 열 때 그 묶음의 지금 값으로 버전 표시를 만든다. 사업 정보는 9칸 값, 진행현황은 최신 판정 줄 id, 실행부서는 최신 부서 줄 id, 신재생은 `energy_value` 문자열을 이어 만든 해시다
- 저장할 때 DB에서 다시 만든 버전 표시가 폼의 것과 다르면 저장하지 않는다. 409로 폼을 다시 보이고 "그사이 ○○님이 고쳤습니다. 지금 값을 확인하고 다시 저장하세요"를 적는다. 이름은 그 묶음의 가장 최근 `edit_log`에서 가져온다. 기록이 없으면(수집·이관이 바꾼 경우) "그사이 값이 바뀌었습니다"로 적는다
- 내 입력은 폼에 남긴다. 표 아래에 지금 값이 보인다
- 수집과 저장이 겹치는 DB 잠금은 2단계의 5초 대기를 그대로 쓴다

## 수집 예약: `nara run slot`

| 슬롯 | 단계 |
|---|---|
| `09` | `collect --days 3` → `enrich award --tier focus` → `enrich status --tier focus` |
| `12` | `collect --days 3` → `enrich award --tier rest --group <오늘 요일 1~5>` (토·일은 낙찰 단계를 건너뛴다) |
| `15` | `09`와 같다 |

- 원 명세의 스케줄표를 따른다. 실행부서 조회(`enrich dept`)는 아직 구현되지 않아 빠진다
- 각 단계는 지금 명령과 같은 함수를 부르고 `run_log`에 따로 남는다. 한 단계가 실패해도 다음 단계를 돈다. 슬롯 전체의 종료 코드는 실패한 단계가 하나라도 있으면 1
- 슬롯은 같은 DB에 대해 한 번에 하나만 돈다. 앞 슬롯이 아직 돌고 있으면 새 슬롯은 "앞 슬롯이 돌고 있다"를 `run_log`에 남기고 끝난다(파일 잠금)

## 백업: `nara backup`

- SQLite 백업 API로 `/srv/nara/backup/nara-YYYYMMDD.db`를 만들고 gzip으로 압축한다. 쓰는 중이어도 깨지지 않는다
- 압축본이 열리는 DB인지(`PRAGMA integrity_check`) 확인한 뒤 rclone으로 구글 드라이브의 `nara-backup/`에 올린다
- 서버에는 최근 7일, 드라이브에는 최근 30일을 남긴다
- 결과는 `run_log`의 `backup` 명령으로 남는다. 목록 머리의 "단계별 마지막 실행"에 백업을 더한다. 72시간 넘게 성공이 없으면 빨갛게 보인다(1단계 규칙 그대로)
- rclone 설정이 없으면 서버 안 백업만 만들고 상태를 `partial`로 남긴다
- 복구 방법은 `deploy/setup.md`에 적는다

## 시트 재이관

`nara migrate tsv`는 그대로 둔다. 팀이 웹으로 옮기면 운영에서 쓰지 않는다. 코드 변경은 없다.

## 테스트

- 로그인: 성공, 틀린 비밀번호·없는 이메일·사용 중지가 같은 문구, 15분 5회 잠금과 풀림, 임시 비밀번호 첫 로그인 → 바꾸기 강제, 10자 규칙, 로그아웃
- 보호: 로그인 없이 모든 화면·POST가 로그인 화면으로 간다. 세션 서명 키 없이는 앱이 뜨지 않는다
- 계정 명령: 추가·중복 거부·재발급·중지·목록
- 기록: 저장·판정·부서·신재생·잠금 해제의 `edit_log.user_id`, 수정 이력에 이름
- 동시 수정: 두 사람이 같은 묶음을 연 뒤 차례로 저장하면 두 번째가 409이고 DB 값은 첫 번째 것
- 슬롯: 단계 순서, 한 단계 실패 뒤 계속, 주말 12시 슬롯, 동시에 두 슬롯이 돌지 않음(네트워크는 가짜로 바꾼다)
- 백업: 만든 파일이 압축을 풀면 열리는 DB이고 행 수가 원본과 같다, rclone 없음 → `partial`
- 1·2단계 테스트는 전부 그대로 통과한다
- 서버 설치 자체는 자동 테스트하지 않는다. 사용자가 서버를 만든 뒤 `deploy/setup.md`의 점검 목록으로 확인한다

## 4단계로 넘기는 것

- 웹 계정 관리 화면
- 실행부서 자동 조회(`enrich dept`)와 그 슬롯 단계
- 수집·백업이 멈췄을 때 메일 알림
- 비밀번호 찾기(메일 발송). 지금은 관리자가 `nara user reset`으로 재발급한다
