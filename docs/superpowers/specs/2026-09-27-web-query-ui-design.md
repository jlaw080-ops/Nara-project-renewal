# 웹 조회 화면 설계 — 1단계

- 작성일: 2026-09-27
- 상태: 설계 확정, 구현 계획 작성 전
- 상위 문서: `docs/superpowers/specs/2026-09-17-nara-collector-design.md` 의 `## 조회 화면`

## 요약

- **주제**: 수집한 사업을 브라우저에서 조회하는 로컬 웹 화면. 웹 UI 3단계 중 첫 단계
- **배경**: 지금은 판정 결과를 보려면 SQL을 직접 쳐야 한다. `nara enrich status`는 요약 한 줄만 찍고 구글시트로 내보내는 경로는 아직 없다
- **결론**: `nara serve`로 띄우는 읽기 전용 화면을 만든다. 행은 사업 하나다. 조건·정렬은 URL에 담는다. DB는 읽기 전용으로 열어 이 단계의 어떤 버그도 자료를 바꿀 수 없게 한다

## 3단계 중 어디인가

웹 UI는 세 단계로 나눠 만든다. 각 단계가 그 자체로 쓸 수 있어야 한다.

| 단계 | 내용 | 이 문서 |
|---|---|---|
| 1 | 조회 화면. 로컬. 읽기 전용 | **해당** |
| 2 | 입력 기능. 착공일·준공일·연면적·ZEB·신재생·비고, 사람 판정 | 별도 문서 |
| 3 | 클라우드 배포·로그인·팀 공유 | 별도 문서 |

1단계가 끝나면 사용자 혼자서는 시트 없이 자료를 볼 수 있다. 시트를 완전히 대신하는 것은 3단계다. 그때까지 시트는 공유·보고용으로 남는다.

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 행의 단위 | 사업(`project`). 249행 |
| 공고 정보 | 사업마다 가장 최근 공고 하나를 붙인다 |
| 기술 | Flask + Jinja2. 서버가 HTML을 그려 보낸다 |
| 상태 보관 | 조건·정렬·방향을 모두 URL 쿼리스트링에 담는다 |
| DB 접근 | 읽기 전용(`mode=ro`) |
| 실행 | `nara serve` — 기존 CLI에 명령 하나 추가 |
| 기간 기준 | 공고일 |
| 이름 검색 | 공고명과 사업명을 함께 찾는다 |

## 원 명세 대비 달라진 점

원 명세의 `## 조회 화면`과 오늘 설계가 어긋나는 곳이다. 섞지 않고 하나씩 정했다.

| 항목 | 원 명세 | 이 문서 | 근거 |
|---|---|---|---|
| 기간 기준 | 공고일 또는 개찰일 | 공고일만 | 2026-09-27 사용자가 "공고일 기준"으로 명시. 더 최근 결정을 따른다. 개찰일 기준은 2단계 이후로 미룬다 |
| 수요기관 | 검색·다중선택 | 다중선택 | 원 명세를 따른다. 오늘 제시한 단일 선택은 사용자 요구가 아니라 제안이었다 |
| 필터 | 진행현황·관심/비관심·낙찰유무·부서확인 | 진행현황·관심/비관심만 | 앞의 둘은 "설계 단계인 사업을 찾는다"는 쓰임에 바로 닿는다. 뒤의 둘은 미룬다(아래 표) |
| 목록 열 | 실행부서·예정공사비·신재생 예상가 포함 | 실행부서는 넣고 나머지 둘은 상세로 | 예정공사비는 158건 중 35건만 채워져 있어 목록에서는 거의 빈 칸이다 |
| 목록 머리 | 단계별 마지막 실행 시각 | 그대로 넣는다 | 원 명세가 핵심 위험으로 꼽은 "자동 실행이 조용히 멈추는 것"을 보이는 장치다 |
| 갱신 방식 | 필터·정렬만 부분 갱신 | 페이지 전체를 다시 그린다 | 249행에서는 차이가 없다. URL이 곧 상태라는 성질을 단순하게 지킨다. 부분 갱신은 서버를 바꾸지 않고 나중에 얹을 수 있다 |

## 1단계에 넣지 않는 것

원 명세나 오늘 논의에 있었지만 이 단계에서 만들지 않는 것 전부다. 빠뜨린 게 아니라 옮긴 것이다.

| 항목 | 옮겨갈 단계 | 이유 |
|---|---|---|
| 입력 기능 전부 | 2 | 이 단계는 읽기 전용이다. 쓰기를 여는 것은 의식적인 변경이어야 한다 |
| 신재생 설비 입력 | 2 | 입력 기능이다. 이미 있는 계획의 예상가 표시는 1단계에 넣는다(상세 화면) |
| 부서 후보 확정 | 2 | 입력 기능이다 |
| 필터: 낙찰업체 유무 | 2 | 오늘 요청에 없었다. WHERE 한 줄이라 언제든 얹는다 |
| 필터: 부서 확인 여부 | 2 | 위와 같다 |
| 기간 기준: 개찰일 | 2 | 위와 같다 |
| 기관 관리 화면 | 2 | 관심/비관심·요일 그룹을 바꾸는 쓰기 기능이다 |
| 설정 화면 | 2 | 제외 키워드·단가표를 바꾸는 쓰기 기능이다 |
| 필터·정렬 부분 갱신 | 2 | 위 표 참조 |
| PDF 리포트 | 2 | 부서 조회(파이프라인 4단계)와 함께 Playwright가 들어올 때 |
| 구글시트 내보내기 | 3 | 시트를 대신하는 것이 3단계의 일이다 |
| 클라우드 배포·로그인 | 3 | 1·2단계를 써 본 뒤 정한다 |
| 쪽 나누기(페이지네이션) | 필요할 때 | 지금 249행이다. 대신 1,000행 상한을 두고 넘으면 화면에 말한다 |

## 구조

```
nara/web/
  __init__.py
  app.py          Flask 앱. 라우트 둘(목록·상세). 얇게 둔다
  query.py        조회 조건 → SQL. DB도 HTTP도 모르는 순수 함수
  templates/
    base.html
    list.html
    detail.html
nara/cli.py       serve 명령 추가
```

**경계는 `query.py`다.** 조회 조건을 SQL과 인자 목록으로 바꾸는 일만 한다. 기존 `nara/verdict.py`가 I/O 없는 순수 함수인 것과 같은 방식이다. 조건 조합·정렬 허용 목록·검색어 이스케이프를 여기서 테스트한다.

`app.py`는 요청을 받아 `query.py`에 넘기고 결과를 템플릿에 넘기는 일만 한다.

## 데이터

### 행 하나

사업 하나가 한 행이다. 249건 중 154건은 공고에서 왔고 95건은 시트에서 이관했다. 이관한 95건에는 공고가 없다.

행에 붙이는 것:

| 붙이는 것 | 고르는 규칙 |
|---|---|
| 공고 | 그 사업의 공고 중 공고일이 가장 늦은 것. 같으면 `bid_no`가 큰 것. 유찰 재공고가 있는 사업이 3건이다 |
| 진행현황 | `status_check`에서 `checked_at` 내림차순, 같으면 `id` 내림차순의 첫 줄. 파이프라인 전체가 쓰는 규칙과 같다 |
| 낙찰업체 | 위에서 고른 공고의 `award.winner` |
| 실행부서 | 그 사업의 `dept_check` 중 가장 최근 것의 `exec_dept` |

판정이 없는 사업이 97건이다. 진행현황 칸에 "판정 전"으로 적는다.

### 기간 조건과 공고 없는 사업

기간은 **행에 보이는 그 공고의 공고일**로 거른다. 보이는 값과 거른 값이 다르면 "조건은 1월인데 왜 5월 공고가 보이지"가 된다.

기간을 걸면 공고가 없는 사업은 빠진다. 공고일이라는 값이 없기 때문이다. 이 사실을 결과 머리에 건수와 함께 적는다. 건수는 고정값 95가 아니라 그때의 다른 조건에 걸리는 공고 없는 사업 수를 센다.

## 목록 화면

주소는 `/`다.

### 맨 위: 단계별 마지막 실행

```
수집 2026-09-26 06:10 정상 · 낙찰 조회 2026-09-26 06:14 정상 · 진행현황 2026-09-25 22:31 일부 실패
```

`run_log`에서 명령별 가장 최근 실행의 시작 시각과 상태를 보인다. 상태가 `ok`가 아니면 눈에 띄게 표시한다. 한 번도 돈 적 없는 명령은 "실행 기록 없음"으로 적는다.

### 열

| 수요기관 | 사업명 | 공고일 | 개찰일 | 진행현황 | 낙찰업체 | 실행부서 | ZEB |
|---|---|---|---|---|---|---|---|

사업명을 누르면 상세로 간다. 값이 없는 칸은 빈 칸이 아니라 "—"로 적는다.

### 조회 조건

| 조건 | 쿼리스트링 | 동작 |
|---|---|---|
| 수요기관 | `org=3&org=7` | 여러 개를 고른다. 69곳 |
| 관심기관만 | `focus=1` | `org.tier='focus'`인 42곳만 |
| 이름 검색 | `q=체육관` | 공고명과 사업명을 함께 찾는다 |
| 기간 시작 | `from=2026-01-01` | 공고일 이상 |
| 기간 끝 | `to=2026-06-30` | 공고일 이하 |
| 진행현황 | `verdict=착공 전(설계 단계)` | 여러 개를 고른다. "판정 전"도 고를 수 있다 |

조건끼리는 AND로 묶는다. 같은 조건 안의 여러 값(수요기관 여럿, 진행현황 여럿)은 OR로 묶는다.

**이름 검색은 공고명과 사업명을 함께 찾는다.** 공고명만 찾으면 시트에서 이관한 95건은 이름으로 영영 찾을 수 없다. 그 사업들에는 공고명이 없다.

목록에는 사업명만 보이므로, 공고명으로만 걸린 행은 왜 걸렸는지 알 수 없다. 그런 행은 사업명 아래에 걸린 공고명을 작게 함께 보인다.

검색어 안의 `%`와 `_`는 글자 그대로 찾는다. SQL `LIKE`의 와일드카드로 해석하면 "100%"를 찾을 때 엉뚱한 행이 걸린다.

잘못된 날짜(`from=어제`)는 그 조건을 무시하고 결과 머리에 "시작일 형식이 맞지 않아 무시했습니다"라고 적는다. 오류 화면을 띄우지 않는다.

### 정렬

| 쿼리스트링 | 정렬 기준 |
|---|---|
| `sort=org` | 수요기관 |
| `sort=name` | 사업명 |
| `sort=notice_date` | 공고일 (기본) |
| `sort=open_date` | 개찰일 |
| `sort=verdict` | 진행현황 |

방향은 `desc=1`이면 내림차순이다. 기본은 공고일 내림차순(최근 것 먼저)이다. 열 머리를 누르면 그 열로 정렬하고 이미 그 열이면 방향을 뒤집는다.

**진행현황은 단계순으로 정렬한다.** 착공 전 → 시공 중 → 준공 완료 → 미확인. 가나다순이면 "미확인·시공 중·준공 완료·착공 전"이 되어 쓸모가 없다. 내림차순이면 이 순서를 뒤집는다.

값이 없는 행은 방향과 관계없이 맨 뒤에 둔다. 공고일 없는 사업, 판정 전인 사업이 여기에 든다. "판정 전"을 단계 순서에 넣으면 내림차순에서 맨 앞으로 올라와 판정된 사업을 가린다. 정렬이 같으면 사업 `id`로 순서를 고정한다 — 새로고침할 때마다 순서가 바뀌면 안 된다.

**정렬 기준은 위 표의 다섯 값만 받는다.** 그 밖의 값은 기본값으로 바꾸고 결과 머리에 적는다. 사용자 입력을 SQL의 `ORDER BY`에 그대로 붙이면 주입 구멍이 된다.

### 결과 머리

```
249건 중 37건     조건: 완주군 · "체육관" · 공고일 2026-01-01~
공고일 조건이 걸려 공고가 없는 사업 12건이 제외되었습니다
```

- 전체 건수와 걸린 건수를 늘 보인다
- 걸린 조건을 한 줄로 되풀이한다
- 조건 때문에 빠진 것이 있으면 그 이유와 건수를 적는다
- 결과가 1,000건을 넘으면 1,000건까지만 보이고 "1,000건만 표시합니다. 조건을 좁혀 주세요"라고 적는다

조용히 빠지는 행이 없어야 한다. 이 도구가 처음부터 지킨 원칙이다.

## 상세 화면

주소는 `/project/<id>`다. 없는 `id`면 404다.

| 묶음 | 내용 |
|---|---|
| 사업 | 수요기관, 사업명, 주소, 착공일, 준공일, 연면적, ZEB 등급, 신재생 비율, 기타 인증, 관급 장비, 비고, 출처(`g2b`/`manual`) |
| 공고 | 그 사업의 공고 **전부**. 공고명·공고일·개찰일·마감일·예산·담당자·원문 링크. 유찰 재공고가 있으면 여러 줄이다 |
| 낙찰 | 공고별 낙찰업체·낙찰일 |
| 진행현황 이력 | `status_check` **전부**. 시각·판정·판정 주체·사유·근거 URL |
| 실행부서 | `dept_check` 전부. 실행부서·계약부서·스니펫·출처 |
| 신재생 계획 | `energy_plan` 전부. 에너지원·용량·예상가. 59건에 자료가 있다 |

예상가는 기존 `nara/energy.py`의 `estimate_cost`로 계산한다. 읽기만으로 나오는 값이라 1단계에 넣는다. 이 함수는 단가표에 없는 에너지원을 빼고 합한다. 그대로 합계만 보이면 금액이 왜 적은지 알 수 없으므로, 단가가 없어 계산에서 빠진 에너지원을 합계 옆에 적는다.

진행현황 이력과 공고 전부는 지금 어디에서도 볼 수 없는 정보다. `status_check`는 이력이 쌓이는 표인데 파이프라인은 최신 한 줄만 쓴다. 사람이 조사한 판정과 기계가 내린 판정, 그리고 판정이 언제 어떻게 바뀌었는지가 이 화면에서 처음 보인다.

판정 주체는 사람이 읽을 말로 바꿔 적는다.

| `decided_by` | 화면 |
|---|---|
| `imported` | 시트 이관 |
| `rule` | 규칙 |
| `news` | 뉴스 |
| `llm` | LLM |
| `human` | 사람 |

근거 URL은 `evidence_json`의 `url`에서 꺼낸다. 없거나 비어 있으면 적지 않는다.

## 안전장치

| 위험 | 막는 방법 |
|---|---|
| 조회 화면의 버그가 자료를 바꾼다 | DB를 `mode=ro`로 연다. 쓰기 SQL이 실행되면 SQLite가 거부한다 |
| 정렬 인자로 SQL 주입 | 정렬 기준은 허용 목록의 다섯 값만 받는다 |
| 검색어로 SQL 주입 | 모든 값을 자리표시자(`?`)로 넘긴다. 문자열을 SQL에 이어 붙이지 않는다 |
| 검색어의 `%`·`_`가 와일드카드가 된다 | `LIKE ... ESCAPE`로 글자 그대로 찾는다 |
| 템플릿에 기사 제목 등이 섞여 스크립트가 실행된다 | Jinja2 자동 이스케이프를 끄지 않는다 |
| 외부에서 접속된다 | `127.0.0.1`에만 묶는다. 다른 주소에 묶는 것은 3단계의 일이다 |
| 수집이 멈췄는데 모른다 | 목록 맨 위에 단계별 마지막 실행과 상태를 보인다 |

## 테스트

| 대상 | 방법 |
|---|---|
| `query.py` | 순수 함수라 DB 없이 SQL과 인자를 확인한다. 조건 조합, 정렬 허용 목록, 검색어 이스케이프, 잘못된 날짜 |
| 조회 결과 | 테스트용 SQLite에 사업·공고·판정을 넣고 조건별로 걸리는 행을 확인한다 |
| 라우트 | Flask `test_client()`로 목록·상세를 불러 상태 코드와 내용을 확인한다 |
| 읽기 전용 | 앱이 연 연결로 `INSERT`를 시도해 거부되는 것을 확인한다 |
| 실데이터 | `data/nara.db` 사본으로 서버를 띄워 조건 몇 가지를 손으로 확인한다 |

테스트는 망에 나가지 않는다. 이 화면은 외부 API를 부르지 않는다.

반드시 박아 둘 경우:

- 기간 조건을 걸면 공고 없는 사업이 빠지고 빠진 건수가 머리에 나온다
- 이름 검색이 공고명과 사업명 양쪽에서 걸린다. 공고 없는 사업도 사업명으로 찾힌다
- 진행현황 정렬이 단계순이다
- 정렬 인자에 허용되지 않은 값을 넣으면 기본값이 되고 SQL이 바뀌지 않는다
- 검색어 `100%`가 와일드카드로 해석되지 않는다
- 유찰 재공고가 있는 사업이 목록에 한 줄만 나오고 상세에는 공고가 전부 나온다

## 실행

```bash
uv run nara serve
```

브라우저에서 `http://127.0.0.1:8000`을 연다. 포트와 DB 경로는 다른 명령과 같은 방식으로 바꾼다.

```bash
uv run nara serve --port 8080 --db data/nara.db
```

## 확인이 필요한 것

- **Flask가 Python 3.14에서 설치되는지 아직 확인하지 않았다.** 구현 계획의 첫 작업에서 확인한다. 안 되면 FastAPI + Jinja2로 바꾼다. 구조와 경계는 같다.

## 2·3단계로 넘기는 판단

1단계에서 결정하지 않지만 뒤 단계에서 반드시 다뤄야 하는 것들이다.

- **개인정보.** `notice`에 공무원 담당자명 35건·연락처 35건, `dept_check`에 연락처 185건이 있다. 3단계에서 클라우드에 올리면 로그인 뒤에 있어도 외부 서버에 저장된다. 사내 규정 확인이 필요하다
- **공개 저장소.** 이 저장소는 공개(public)다. 3단계의 배포 설정·DB 접속 정보가 커밋되면 즉시 노출된다
- **수집을 어디서 돌릴 것인가.** 지금 수집은 사용자 PC에서 `G2B_API_KEY`로 돌아 로컬 파일에 쓴다. 3단계에서 DB가 클라우드로 가면 수집도 옮기거나, 로컬이 클라우드로 밀어 넣거나, 전부 옮겨야 한다
- **동시 수정.** 2단계의 입력을 3단계에서 여러 사람이 쓰면 같은 칸을 둘이 고치는 경우를 정해야 한다
