# 나라장터 설계용역 수집·조사 앱 설계

- 작성일: 2026-09-17
- 상태: 설계 확정, 구현 계획 작성 전
- 대체 대상: 구글시트 내장 Apps Script(`나라장터_설계용역_경기도_시별_26_06_10`)

## 요약

- **주제**: 나라장터 설계용역 공고를 자동으로 모으고 낙찰업체·진행현황·실행부서까지 조사해 한 곳에서 조회하는 로컬 앱의 설계
- **배경**: 지금은 Apps Script가 공고를 수집해 구글시트에 쌓고 그 뒤의 조사(진행현황 실증, 공고문에서 실행부서 찾기)는 사람이 Claude와 함께 건건이 한다. 두 작업이 끊겨 있어 조사 결과가 시트에 손으로 옮겨지고 그 과정에서 행이 어긋나는 사고가 반복됐다
- **결론**: 수집부터 조사까지를 한 파이프라인으로 묶고 데이터 정본을 앱 SQLite로 옮긴다. 스케줄은 윈도우 작업 스케줄러가 쥐고 각 단계는 터미널에서 다시 돌려볼 수 있는 CLI로 만든다

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 데이터 정본 | 앱 SQLite. 구글시트는 내보내기 대상 |
| 실행 환경 | 사용자 PC 로컬. 윈도우 작업 스케줄러 + 로컬 조회 서버 |
| 구조 | 파이썬 2프로세스 — 수집·조사 CLI + 조회 서버 |
| 진행현황 판정 | 규칙으로 먼저 가르고, 애매한 건만 LLM |
| 수집 범위 | 전국 수집. 심화 조사는 관심 기관 위주 |
| 비관심 기관 | 낙찰결과만 자동 조사. 전 단계 조사는 기관을 골라 수동 지시 |
| PDF | 조회 결과를 리포트 PDF로 |
| 기존 시트 | 전 탭 통째로 이관 |
| 제외 키워드 | 현재 설정을 그대로 사용 |

## 왜 이 구조인가

핵심 위험은 화면이 부족한 것이 아니라 **자동 실행이 조용히 멈추는 것**이다. 스케줄을 앱 안에 두면 그 프로세스가 죽을 때 수집도 함께 멈추고 며칠 뒤에야 알게 된다. 운영체제가 스케줄을 쥐면 PC를 껐다 켜도 살아 있고 놓친 회차를 따라잡는 기능도 이미 있다.

2026년 9월 15~16일 작업에서 드러난 문제도 모두 "실행을 되짚을 수 있는가"의 문제였다. 붙여넣기 한 칸이 밀린 사고, 근거 없이 준공으로 판정된 건, 단가가 바뀌면 33건을 다시 계산해야 하는 구조 — 이 설계는 세 가지를 각각 구조로 막는다.

### 데이터 흐름

나라장터 API가 준 것은 `notice`에 원본 그대로 넣고 단계별 조사 결과는 근거와 함께 별도 표에 쌓는다. 조회 화면과 내보내기는 이 둘을 합쳐서 본다.

조사 결과를 원본과 같은 표에 덮어쓰지 않는 이유가 둘 있다. 판정이 바뀌었을 때 언제 무슨 근거로 그렇게 봤는지 남아야 되짚을 수 있고 사람이 넣은 값을 자동 조사가 덮어쓰는 사고가 구조적으로 막힌다.

### 실행 흔적

모든 CLI 실행은 `run_log`에 시작·끝·처리 건수·오류를 남긴다. 조회 화면 맨 위에 단계별 마지막 실행 시각을 띄워 자동 실행이 멈춘 것을 바로 알 수 있게 한다.

### 공고와 사업을 나누는 이유

기존 시트에는 두 종류 행이 섞여 있다. 공고번호가 있는 나라장터 행과, 공고번호 없이 손으로 넣은 건축물 행(고창터미널·전주시립미술관 등 33건)이다. 한 사업에 공고가 여럿 붙는 경우도 실재한다(대야철길숲 3건, 용궐산 3건). `project`를 조사 단위로 두면 둘 다 담기고 수기 데이터가 공고 재수집에 휩쓸리지 않는다.

1차에서는 공고 한 건이 사업 한 건을 만든다. 여러 공고를 한 사업으로 묶는 화면은 나중에 붙인다.

### 판정을 이력으로 쌓는 이유

진행현황은 덮어쓰지 않고 한 줄씩 추가하고 화면은 최신 것만 보여준다. 회차를 거듭하며 판정이 뒤집히면 언제 무엇을 보고 바뀌었는지가 남는다.

### 예상가를 저장하지 않는 이유

용량과 단가만 저장하고 금액은 조회할 때 곱한다. 2026-09-16 작업에서는 계산 결과를 셀에 넣었는데, 단가가 바뀌면 33건을 다시 계산해 다시 붙여넣어야 한다. 단가표만 고치면 전부 따라오게 한다.

현재 단가(`재생에너지원별단가` 탭 기준): BIPV 5,000,000원/kW, PV 2,500,000원/kW, 지열 2,500,000원/kW, PEMFC 32,000,000원/kW, SOFC 98,250,000원/kW.

## 기존 시트 이관

`nara migrate sheets`를 1회 실행한다. 전 탭을 TSV로 받아 위 표들로 흩뿌린다.

| 시트 열 | 가는 곳 |
|---|---|
| 공고번호 있는 행 | `notice` + `project` |
| 공고번호 없는 행 | `project` (source=manual) |
| 주소·착공일·준공일·연면적 | `project` |
| 진행현황 | `status_check` (판정주체 = imported) |
| 담당부서·부서장·전화번호 | `dept_check` (판정주체 = imported) |
| 낙찰업체 설계사무소 | `award` |
| 설치계획내용 | `energy_plan` — `PV: 21.96kW BIPV: 72.6kW`를 두 행으로 분해 |
| ZEB 인증등급·신재생 공급의무비율·기타 인증요건·지침서 명시 설비 | `project` 부가 항목 |
| 설정 탭의 제외 키워드 | `config.toml` |

**TSV 줄 분할을 반드시 처리한다.** 설치계획내용 칸에 줄바꿈이 들어 있으면 구글 TSV가 한 행을 두 줄로 내보낸다. 2026-09-16 작업에서 이것을 놓쳐 한 칸이 밀렸다. 헤더보다 필드 수가 적은 줄은 다음 줄과 합치고 이관 후 시트 행 수와 DB 건수를 대조한 리포트를 낸다.

이관은 되돌릴 수 있게 원본 TSV를 그대로 보관한다.

## 파이프라인

### 1단계 · 수집

기존 Apps Script의 수집부를 옮기되 수요기관 포함 필터만 뺀다(전국 수집이므로).

- 목록 API: `getBidPblancListInfoServcPPSSrch`, `inqryDiv=1`
- `srvceDivNm`이 `기술용역`인 것만
- 취소공고 제외
- 제목 필수 `설계`, 제목 제외 키워드 60여 개 (현재 설정 그대로)
- 수요기관 제외 키워드 (교육청·개발공사·경찰청 등, 현재 설정 그대로)

처음 보는 수요기관은 자동 등록하고 비관심·요일그룹을 배정한다. 같은 공고번호가 다시 오면 원본만 갱신하고 사업·조사 결과는 건드리지 않는다.

**관심 기관 초기값**은 현재 Apps Script가 쓰는 19개다 — 용인시·영천시·남양주시·부산광역시·대전광역시·성남시·의왕시·수원시·화성시·평택시·안성시·하남시·군포시·시흥시·오산시·파주시·전라북도·전북특별자치도·전주시. 화면에서 언제든 바꾼다.

### 1단계-B · 소급 수집

전국 수집으로 바꾸면 지금까지 관심 기관 밖이라 받지 않았던 과거 공고가 없다. `nara backfill --days 365`로 최근 1년을 한 번 받아온다.

- 기간을 3일 단위로 쪼개 과거에서 현재 방향으로 훑는다
- 진행 위치를 저장하므로 중단해도 다음 실행에서 이어진다
- 소급으로 들어온 공고도 같은 필터를 거치고 낙찰·진행현황·부서는 평소 스케줄이 순서대로 따라잡는다

수집 자체는 API 호출이라 가볍다. 무거운 것은 그 뒤의 조사이고 그것은 관심 기관과 요일 그룹으로 이미 나뉘어 있다.

### 2단계 · 낙찰업체

개찰일이 지났고 낙찰업체가 비어 있는 공고만 조회한다. 결과가 없으면 그대로 두고 다음 회차에 다시 본다.

- 낙찰 API: `getScsbidListSttusServc`, `inqryDiv=4`
- 낙찰업체명(`bidwinnrNm`)이 있는 항목 중 가장 최근 등록 건을 쓴다

### 3단계 · 진행현황

**규칙이 바로 판정하는 경우**

| 확인한 사실 | 판정 |
|---|---|
| 낙찰업체가 기록됨 | 착공 전(설계 단계) — 낙찰 근거 |
| 개찰일이 지났고 낙찰업체 미확인 | 착공 전(설계 단계) — 개찰 근거 |
| 공고일만 있고 개찰 전 | 미확인 |

**LLM으로 넘기는 경우** — 규칙이 틀렸던 유형이다.

| 상황 | 2026-09-16 사례 |
|---|---|
| 기사에 `착공`과 `예정`이 함께 있음 | 완주군 다목적체육관 — "2026년 9월 착공"이 예정인지 실제인지 |
| 기사 연도가 사업 일정과 크게 어긋남 | 진안복합노인 복지센터 — 2006년 개원 시설이 검색됨 |
| 준공 기사와 착공 기사가 동시에 잡힘 | 순창군 동계면 종합체육관 |
| 사업명이 부분만 일치 | 남원 동부권 학교복합시설 |

**덮어쓰지 않는 규칙**

- 개찰일·낙찰일을 착공일로 쓰지 않는다
- 판정이 `착공 전`이면 확정 착공일을 기록하지 않는다. `2027년 착공 예정` 같은 예정 표기만 허용한다
- 근거 URL 없는 `준공 완료`·`시공 중` 주장은 `착공 전`으로 내린다
- 사람이 넣은 착공일·준공일과 보도가 어긋나면 사용자 값을 고치지 않고 불일치로 기록한다

뉴스 검색은 네이버 검색 API를 쓴다. 키가 없으면 그 단계를 건너뛰고 규칙 판정만 남기며 화면에 그 사실을 표시한다.

### 4단계 · 부서 조회

`notice-dept-contact-lookup` 스킬의 검증된 경로를 옮긴다.

공고 URL을 Playwright로 열고 첨부 그리드에서 **체크박스를 클릭한 뒤 다운로드 버튼**을 누른다. 미리보기 경로는 오버레이에 가려 동작하지 않고 다운로드 URL은 암호화 POST라 조립할 수 없다.

- 파일 선택 우선순위: `공고` 포함 → 없으면 `과업|지침|제안`. PDF를 HWP보다 먼저
- 그리드 id의 uuid는 로드마다 바뀌므로 `[id$="_grdFile_body_tbody"]` 접미사 선택자로 잡는다
- 파일 목록은 DOM이 아니라 `getRowJSON(i)`의 `orgnlAtchFileNm`으로 읽는다
- 공고문은 계약부서와 실행부서를 짝으로 적는다. 이 대비 구조를 찾는다

**스크립트는 후보만 좁히고 근거 스니펫을 함께 저장한다.** 후보가 하나이고 스니펫이 명확할 때만 자동 확정하고 애매하면 `검토 필요`로 두어 화면에서 스니펫을 보고 고르게 한다. 조직도나 사업 성격으로 역추론하지 않는다. 근거를 못 찾으면 빈칸이다.

첨부는 받아서 보관한다. 같은 공고를 다시 조사할 때 재다운로드하지 않고 ZEB·신재생 조항을 나중에 뽑을 때도 원본이 필요하다.

작업 스케줄러에는 "예약된 시작 시간을 놓친 경우 가능한 한 빨리 작업 시작"을 켠다.

### 중단과 이어하기

각 단계는 시간 예산(기본 20분)을 받고, 넘기면 처리한 만큼 저장하고 멈춘다. 다음 회차는 미처리 대상을 다시 집어오므로 자연히 이어진다.

첨부 다운로드가 실패하면 3회까지 재시도하고 그래도 안 되면 `수동 확인`으로 표시한다. 한 단계가 실패해도 다음 단계는 진행하고 무슨 일이 있었는지는 `run_log`에 남는다.

## 조회 화면

로컬 서버(`localhost:8000`)에 네 화면을 둔다. 서버에서 HTML을 그려 보내고 필터·정렬만 부분 갱신한다.

**목록** — 기본 화면

- 필터: 수요기관(검색·다중선택), 기간(공고일 또는 개찰일 범위), 진행현황, 관심/비관심, 낙찰업체 유무, 부서 확인 여부
- 열: 수요기관 / 사업명 / 공고일 / 개찰일 / 낙찰업체 / 진행현황 / 실행부서 / 예정공사비 / 신재생 예상가
- 맨 위에 단계별 마지막 실행 시각

**상세** — 공고 원본, 진행현황 판정 이력(근거 URL 포함), 부서 근거 스니펫 원문, 받아둔 첨부 파일, 신재생 설비 계획 입력.

부서는 후보와 스니펫을 함께 보여주고 사람이 확정한다. 신재생 설비는 에너지원과 용량만 넣으면 단가표를 곱해 예상가를 보여준다.

**기관 관리** — 관심/비관심 토글, 요일 그룹, 내보낼 시트 탭 지정, `[이 기관 전 단계 조사]` 버튼.

**설정** — 제외 키워드, 단가표, API 키 연결 상태.

### PDF 리포트

지금 걸려 있는 필터 결과를 PDF로 만든다. 열을 골라 담을 수 있고 머리말에 필터 조건과 생성 시각이 찍힌다.

HTML로 A4 가로 레이아웃을 그린 뒤 Playwright로 PDF를 렌더한다. 부서 조회 때문에 Playwright가 이미 있고 시스템 폰트를 그대로 쓰므로 한글 폰트 문제가 없다. 같은 HTML을 화면에서 미리 볼 수도 있다.

## 구글시트 내보내기

**Sheets API로 쓴다. 브라우저 클립보드 붙여넣기를 쓰지 않는다.** 2026-09-16 하루에 두 번 겪은 행 어긋남(TSV 줄 분할, 동시 편집 중 행 삭제)은 클립보드 방식 때문에 생긴 문제이고 API로 쓰면 범위를 명시하므로 사라진다.

앱 DB가 정본이므로 내보내기는 탭을 덮어쓴다. 시트에서 직접 고친 값은 다음 내보내기에 사라지므로, 덮어쓰기 직전에 현재 시트를 로컬에 TSV로 백업하고 화면에도 이 사실을 표시한다.
