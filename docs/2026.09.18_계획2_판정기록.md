### 사전 점검이 찾은 것

**P1 — Task 11의 시간 예산 테스트가 now_fn 호출 횟수에 묶여 있다.**
`ticks = iter([...])` 7개를 주는데, 구현이 now_fn을 다르게 부르면 StopIteration으로
엉뚱하게 죽는다. 테스트가 검증하려는 것은 "예산을 넘기면 멈추고, 그때까지 쓴 것은
남는다"이지 "now_fn을 정확히 7번 부른다"가 아니다.
Ruling R1: 구현자가 가짜 시계의 모양을 바꿔도 된다(예: 호출마다 증가하는 카운터).
  단 세 단언(stopped_early is True / checked < 5 / status_check 수 == recorded)은
  약화하지 않는다. — 계획이 못 박은 테스트 도우미가 구현 세부에 묶여 있었다.
  비용: 없음. 그대로 뒀으면 구현이 맞는데도 테스트가 StopIteration으로 죽는다.

**P2 — Task 12의 `test_enrich_status_reports_counts`가 "3" in output을 단언한다.**
출력 어디에든 3이 있으면 통과한다 — 리뷰 루브릭이 "아무것도 검증하지 않는 테스트"로
잡을 자리이고, 실제로 그렇다.
Ruling R2: 단언을 실제 문구로 좁힌다 — "확인 3건"이 출력에 있는지 본다.
  비용: 없음. 그대로 뒀으면 카운터가 망가져도 통과한다.

**P3 — Task 14의 순창군 케이스는 이름과 다른 이유로 통과한다(관찰, 차단 아님).**
기사 둘의 연도(2020, 2025)가 사업 일정(2025-07-17~)과 3년 넘게 벌어져 "연도 어긋남"
분기에서 먼저 needs_llm=True가 된다. "착공·준공 동시" 분기까지 가지 않는다.
Ruling R3: 그대로 둔다. 실제 2026-09-16 데이터가 그랬고(시트 2025.07.17 ↔ 보도 2020
  착공·2025.06.25 준공), 회귀 테스트의 목적은 "그때 그 입력에서 기계가 단정하지 않는
  것"이다. 어느 분기가 잡든 목적은 달성된다. 다만 "착공·준공 동시" 분기 자체는
  Task 4의 test_read_news_defers_when_completion_and_start_collide가 따로 덮는다.
  비용: 낮음. 연도 분기를 나중에 고치면 이 테스트가 다른 이유로 깨질 수 있는데,
  그때 깨지는 것이 맞다.

사전 점검 결론: 차단 사유 없음. R1·R2를 해당 작업 디스패치에 실어 보낸다.
